Clean Code 有意義的命名：變數、函式、類別怎麼取名（完整筆記）

發表於 2024-03-04 更新於 2026-11-26 分類於 CleanCode 閱讀次數： Disqus： 文章字數： 4.8k 所需閱讀時間 ≈ 9 分鐘

這篇是《Clean Code》第 2 章「有意義的命名」的完整閱讀筆記：容器型態要不要放進名稱、怎麼做出有意義的區別、類別和方法該用名詞還是動詞、介面要不要加 I、一個概念只用一個字詞、上下文資訊怎麼加才對，最後附上一份命名檢查清單。

不要把容器型態放進名稱

accountList 把型態寫進名稱，但如果它其實不是 List，名稱就會誤導人；就算是 List，以後換成別的容器時名稱也得跟著改。

產生有意義的區別

無意義的字詞也一樣。Product、ProductInfo、ProductData 名稱不同，卻看不出三者有什麼差別；Info、Data 這類字和 a、an、the 一樣，加了等於沒加。

呼叫的人要怎麼知道該用哪一個？名稱要能清楚區分它們的差異，否則就應該合併或重新命名。

介面與實作的命名

建立 Abstract Factory 時，介面要叫 IShapeFactory 還是 ShapeFactory？

建議不加 I。多餘的字首 I 只會讓人分心，使用者不需要知道它是介面，只需要知道它是一個 ShapeFactory。如果介面和實作一定要有一個帶標記，寧可標在實作上，例如 ShapeFactoryImp 或 CShapeFactory，都比 IShapeFactory 好。

類別用名詞，方法用動詞

  • 類別和物件：用名詞或名詞片語，例如 Customer、WikiPage、Account、AddressParser。避免 Manager、Processor、Data、Info 這類模糊的字，類別名稱也不該是動詞。
  • 方法：用動詞或動詞片語，例如 postPayment、deletePage、save。

每個概念使用一種字詞

替同一個抽象概念挑一個字詞，然後一直用它。

  • 不同類別的取值方法分別叫 fetch、retrieve、get，使用的人就得記住是哪個人、哪個團隊寫的類別，或花時間翻程式碼才知道該呼叫哪個。
  • 同一個專案裡同時有 controller、manager、driver，也會讓人困惑：DeviceManager 和 ProtocolController 本質上差在哪？為什麼不統一用同一個字？混用會讓人以為它們是型態不同、職責不同的物件。

用詞一致，對之後要使用你程式碼的工程師是很大的幫助。

別說雙關語

反過來，也不要用同一個字詞代表兩種不同的意思，那就是雙關語。

假設專案裡很多類別都有 add 方法，意思是「把兩個值相加或相連，產生新的值」。如果新類別的方法其實是把一個元素放進集合裡，為了「一致」也叫它 add，就是雙關語。這時應該用 insert 或 append。

我們的目標是讓程式碼盡量好懂，像讀一本好讀的平裝書，而不是像讀學術論文，要努力挖掘才看得出真正的意思。

解決方案領域與問題領域的命名

  • 讀程式的人幾乎都是工程師，所以優先使用電腦科學的術語：演算法名稱、設計模式名稱、數學用語等。工程師都知道 JobQueue 是什麼，替技術性的東西取技術性的名稱，通常最合適。
  • 沒有工程師熟悉的術語可用時，才使用問題領域的術語。至少維護的人可以去問領域專家這個名稱是什麼意思。
  • 分清楚哪些程式碼屬於解決方案、哪些屬於問題領域，是好的工程師和設計者應該做的事。跟問題領域概念關係越密切的程式碼，越應該用問題領域的名稱。

添加有意義的上下文資訊

firstName、lastName、street、houseNumber、city、state、zipCode 放在一起，很明顯是地址。但如果單獨在某個方法裡看到 state，就不一定猜得出來是地址的一部分。

  • 可以加字首提供上下文，例如 addrFirstName、addrState
  • 更好的做法是建立 Address 類別，把相關的欄位和方法都放進去，連編譯器都能理解它們屬於同一個概念

別添加無理由的上下文資訊

反過來，上下文也不能亂加。假設有個叫「BYG」的應用程式，把每個類別都加上前綴：Account 變成 BYGAccount、Address 變成 BYGAddress。結果在 IDE 裡輸入 B，自動補齊會跳出整個專案的類別，反而更難找。

  • 名稱如果夠清楚，短的通常比長的好，不要加入不必要的上下文
  • accountAddress、customerAddress 當成類別的實例名稱很好，但不適合當類別名稱
  • 要區分不同種類的位址時，用更精確的名稱：郵寄地址用 PostalAddress、網卡位址用 MAC、網址用 URI

總結

取好名稱最難的地方，是需要好的描述能力和共同的文化背景。這比較不是技術、商業或管理的問題，而是訓練的問題，很多人從來沒有好好學過怎麼取名。

很多人不敢改名，擔心其他人反對。其實把名稱改得更有意義，其他工程師通常會很感謝。我們本來就不會記住每個類別和方法的名稱，現代 IDE 會幫我們處理這些細節，讓我們能專心把程式寫得像一段文章，或至少像清楚的表格和資料結構。

就像任何重構一樣，別讓改名這件事擋住你。照著這些規則改改看，觀察可讀性有沒有變好：短期就會有成果，長期也會持續受益。

命名檢查清單

  • 名稱裡沒有容器型態（List、Map）之類的實作細節？
  • 沒有 a1、a2 這種數字序列，也沒有 Info、Data 這種無意義的字？
  • 名稱唸得出來、搜尋得到？
  • 介面名稱沒有多餘的 I 字首？
  • 類別是名詞、方法是動詞，取值 / 設值 / 判斷分別用 get / set / is？
  • 同一個概念在整個專案只用一個字（不會 fetch、get、retrieve 混用）？
  • 同一個字不會代表兩種意思？
  • 優先用技術術語，沒有的話用問題領域的術語？
  • 上下文不足時，用類別來提供上下文？
  • 沒有加上不必要的前綴或上下文？
