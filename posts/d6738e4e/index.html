單例模式（Singleton）：private 建構子、多執行緒下的 lock、雙重鎖定與靜態初始化

發表於 2024-11-19 更新於 2026-11-27 分類於 ObjectOrientedProgramming 閱讀次數： Disqus： 文章字數： 3k 所需閱讀時間 ≈ 5 分鐘

這篇是《大話設計模式》單例模式的讀書筆記：如何用 private 建構子讓類別自己負責「只有一個實體」、單例和靜態類別的差別、多執行緒同時呼叫時可能建立出多個實體的問題，以及三種執行緒安全的寫法：lock、雙重鎖定（Double-Check Locking）和靜態初始化。

起點：生不生是自己的責任

以視窗程式的「工具箱」視窗為例：使用者每點一次選單，就 new 一個工具箱視窗，結果畫面上出現好幾個工具箱。

要讓一個類別只有一個實體，與其要求每個呼叫的地方都記得先檢查，不如讓類別自己負責。關鍵是：

  • 所有類別都有建構子；沒寫的話，系統會產生一個預設的空建構子
  • 只要自己定義了建構子，預設的建構子就會失效
  • 把建構子設成 **private**，外部程式就無法 new 它

定義

單例模式：保證一個類別只有一個實體，並提供一個存取它的全域存取點。

用全域變數雖然能讓一個物件被存取，但無法防止別人再建立其他實體。最好的辦法是讓類別自己保存它唯一的實體，保證不會有其他實體被建立，並提供取得這個實體的方法。

好處：受控的唯一實體

  • Singleton 封裝了它唯一的實體，可以嚴格控制用戶端怎麼存取、何時存取

單例 vs 靜態類別

單例靜態類別
狀態是一個物件，可以有狀態通常只提供靜態方法，不保存狀態
繼承與多型可以實作介面、被繼承不能
建立時機可以延遲到第一次使用才建立類別載入時

詳細比較可以參考 C# static class 與一般類別的差異。

多執行緒的問題

上面的寫法在多執行緒下不安全：兩個執行緒同時呼叫 GetInstance()，可能都判斷 instance == null，結果建立出兩個實體。

為什麼鎖裡面還要再判斷一次？假設 instance 是 null，兩個執行緒同時通過第一重判斷。因為 lock，只有一個能進去建立實體，另一個在外面排隊。等第一個出來後，第二個進去時如果沒有再判斷一次，就會又建立一個新的實體。

instance 宣告成 volatile，可以避免指令重排序讓其他執行緒拿到「已經指派、但還沒初始化完成」的物件（Java 也必須加 volatile）。

寫法三：靜態初始化

  • 不需要自己寫任何執行緒安全的程式碼，由 CLR 保證靜態欄位只會被初始化一次
  • sealed 防止被繼承，避免子類別建立出更多實體
  • 這種方式是在類別被載入時就建立實體（俗稱「餓漢式」）；前面的寫法則是第一次被參考時才建立（「懶漢式」）

實務上的提醒

單例本質上是全域狀態，用多了會讓類別之間產生隱藏的依賴，也很難在單元測試裡替換。使用 Spring、.NET 的 DI container 時，通常讓容器以 singleton 範圍管理物件，而不是自己寫單例類別。
