Redisson 分散式鎖完整筆記：RLock、lock 與 tryLock、正確釋放鎖與 Redis Cluster 的限制

可重入鎖（Reentrant Lock）

最常用的鎖。同一個執行緒可以重複取得同一把鎖：

Watchdog：沒有指定 leaseTime 時會自動續期

  • 沒有指定 leaseTime（lock()、tryLock(waitTime, unit)）：Redisson 會啟動 watchdog，持有鎖的期間定期幫鎖續期（預設鎖的有效時間 30 秒，每 10 秒續一次），直到 unlock() 或程式結束。
  • 有指定 leaseTime：時間一到鎖就自動釋放，不會續期。如果業務邏輯跑得比 leaseTime 久，鎖會在執行中途被釋放，其他執行緒就可能同時進入。

注意：一般的 RLock 不保證等待的執行緒依照進來的順序取得鎖。需要先到先得，要用下面的公平鎖。

正確釋放鎖

常見錯誤：沒拿到鎖也去 unlock

unlock() 只能由持有鎖的執行緒呼叫。沒拿到鎖、鎖已經過期，或是由其他執行緒持有時呼叫，都會丟出 IllegalMonitorStateException。

經過測試，以下兩種方式都能確實釋放 RLock：

  1. 在 finally 裡用 isHeldByCurrentThread() 確認後再 unlock()
  2. 用 lock(long leaseTime, TimeUnit unit) 設定 leaseTime，到期自動釋放

上面先 if (!lock.isLocked()) 再 lock.lock(...) 是「先檢查再動作」，兩個執行緒可能同時通過檢查，然後一個拿到鎖、另一個卡在 lock() 等待。想要「沒人持有才執行」，直接用 tryLock 一步完成比較安全：

Redis Cluster（主從架構）上的限制

在單一 Redis 上，分散式鎖可以正常運作。但正式環境為了高可用，通常會用主從架構（Redis Cluster 或 Sentinel），這時分散式鎖有一個缺陷：

  1. 客戶端 A 加鎖，依照路由規則把 mylock 寫進某個 master 節點
  2. master 回應成功後，才非同步把 key 複製到 slave
  3. 如果 master 在複製完成之前當機，叢集會做主從切換，slave 升級成新的 master，但它沒有 mylock
  4. 客戶端 B 在新的 master 上加鎖成功，而 A 也認為自己持有這把鎖

結果同一時間有兩個客戶端都拿到了鎖，可能造成髒資料。主從複製延遲也會造成加鎖、解鎖延遲的問題。

應對方式：

  • 業務本身做好冪等，或在資料層加上版本號、唯一鍵等保護，不要只依賴分散式鎖
  • 對一致性要求極高的情境，考慮使用 RedLock（多個獨立 Redis 節點）或 ZooKeeper、etcd 等基於共識演算法的鎖服務
