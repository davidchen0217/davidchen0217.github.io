Clean Code 物件與資料結構：資料抽象化、反對稱性與 Demeter 法則（完整筆記）

發表於 2024-12-24 更新於 2026-11-26 分類於 CleanCode 閱讀次數： Disqus： 文章字數： 4k 所需閱讀時間 ≈ 7 分鐘

這篇是《Clean Code》第 6 章「物件及資料結構」的閱讀筆記：為什麼「private 欄位 + getter / setter」不等於封裝、物件和資料結構的反對稱性、什麼時候該用物件導向、什麼時候該用結構化程式，以及 Demeter 法則與 DTO。

隱藏實作不只是在變數外面包一層函式而已，而是一種抽象化的過程。類別不該只是用 getter / setter 把變數開放出去，而是提供一個抽象介面，讓使用者不需要知道實作細節，也能操作資料的本質。

資料及物件的反對稱性

  • 物件把資料藏在抽象後面，只公開操作資料的函式。
  • 資料結構公開它的資料，沒有有意義的函式。

這兩者剛好是互補的，也就造成了反對稱性：

容易困難
結構化程式（資料結構 + 函式）新增函式，不需要改既有的資料結構新增資料結構，因為所有函式都要改
物件導向新增類別，不需要改既有的函式新增函式，因為所有類別都要改

以付款手續費為例。結構化的寫法：資料結構只放資料，計算集中在一個地方。

  • 要新增 refundableAmount() 這種新功能：只要在 PaymentCalculator 加一個函式，資料結構完全不用動。
  • 要新增 LinePayPayment 這種新型態：PaymentCalculator 裡的每個函式都要改。

物件導向的寫法：每種付款自己知道怎麼算。

  • 要新增 LinePayPayment：只要加一個類別，其他程式完全不用動。
  • 要新增 refundableAmount()：每個實作類別都要改。

結構化與物件導向，該選哪一個？

在物件導向裡困難的事，在結構化程式裡比較容易；反過來也一樣。

  • 系統裡常常要新增資料型態、而函式相對固定時，物件導向最適合。
  • 系統裡常常要新增函式、而資料型態相對固定時，資料結構搭配結構化程式比較適合。

成熟的工程師都知道：「每件事物都應該是物件」只是一個神話。有時候，你真的只需要簡單的資料結構，再用程式來操作它。

Demeter 法則

Demeter 法則（Law of Demeter）：模組不應該知道它所操作物件的內部結構。具體來說，類別 C 的方法 f 只應該呼叫以下這些物件的方法：

  • C 自己
  • f 自己建立的物件
  • 以參數傳進 f 的物件
  • C 的實體變數所持有的物件

不應該呼叫「別人的方法回傳的物件」的方法，也就是只跟朋友說話，不跟陌生人說話。

火車事故（Train Wreck）

這種一長串的呼叫像一節節車廂，被稱為「火車事故」。呼叫端因此知道了 Order 裡有 Customer、Customer 裡有 Address，只要其中一層結構改變，這行就得跟著改。

是否違反 Demeter 法則，要看這些是物件還是資料結構：

  • 如果是物件，就違反了，因為物件應該隱藏內部結構。
  • 如果只是單純的資料結構（例如 DTO），公開內部結構本來就是它的目的，就不算違反。

如果是物件，與其往內挖，不如直接告訴物件你要什麼，或者問清楚「你拿 city 要做什麼」，把那件事交給物件做：

混合體

最糟的是一半是物件、一半是資料結構的混合體：有做重要事情的函式，同時又有公開欄位或一堆 getter / setter，讓外部函式可以像操作資料結構一樣操作它。這種設計同時有兩邊的缺點：既難新增函式，也難新增資料型態。設計時要清楚決定，這個類別是要隱藏資料、提供行為，還是單純承載資料。

資料傳輸物件（DTO）

只有公開欄位、或只有 private 欄位加 getter / setter、沒有任何函式的類別，就是資料傳輸物件（Data Transfer Object, DTO）。它在與資料庫溝通、解析 API 回應或訊息時非常有用，通常是把原始資料轉換成程式物件的第一站。

Active Record 是一種特殊的 DTO：除了欄位之外，還有 save、find 之類的導覽方法，通常直接對應資料表。常見的錯誤是把商業規則也塞進 Active Record，讓它變成混合體。比較好的做法是把 Active Record 當成資料結構，商業規則放在另外的物件裡，並把 Active Record 藏在它後面。

總結

  • 物件公開行為、隱藏資料：容易新增新型態的物件，不容易新增新行為。
  • 資料結構公開資料、沒有明顯的行為：容易新增新行為，不容易新增新型態。

好的工程師不會偏執地認為非物件導向不可，而是依照當下的需求，選擇最適合的方式。

檢查清單

  • 類別提供的是有意義的行為，而不只是把每個欄位都開 getter / setter？
  • 這個類別是物件（隱藏資料）還是資料結構（公開資料），有沒有變成兩者的混合體？
  • 系統比較常新增型態還是新增功能？選擇的設計方式符合這個方向？
  • 有沒有 a.getB().getC().getD() 這種火車事故？對象是物件的話，能不能改成直接告訴它要做什麼？
  • DTO / Active Record 裡沒有混進商業規則？
