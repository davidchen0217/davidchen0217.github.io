Clean Code 函式：寫出簡短、只做一件事的函式（完整筆記）

發表於 2024-03-31 更新於 2026-11-26 分類於 CleanCode 閱讀次數： Disqus： 文章字數： 8.2k 所需閱讀時間 ≈ 15 分鐘

這篇是《Clean Code》第 3 章「函式」的完整閱讀筆記，整理成一篇方便查閱：函式要多短、怎麼判斷「只做一件事」、switch 怎麼處理、參數該有幾個、Side Effect 與指令查詢分離、用例外取代錯誤碼，最後附上一份可以直接拿來 Code Review 的檢查清單。

三分鐘看不懂，就該重構

看到一個函式，試著用三分鐘理解它在做什麼。如果三分鐘內看不懂，就代表這個函式需要重構，通常用這三個步驟：

  1. 提取 private method
  2. 重新取有意義的名稱
  3. 重新整理程式結構

照這三步驟整理後，效果是三分鐘內就能理解程式的意思：

要簡短，而且要更簡短

函式的首要準則是簡短，第二項準則是比第一項還要更簡短。

函式不要超過 20 行。那應該多長才好？理想上每個函式只有 2～4 行，每個函式都一清二楚、透露出自己的意圖，並帶領你走到下一個函式。上面的範例重構再重構之後：

區塊與縮排

if、else、while 等敘述的區塊都應該只有一行，而這一行通常是一個函式呼叫。這不只讓函式維持簡短，被呼叫的函式如果有好名稱，還能像文件一樣說明意圖。

函式不應該大到包含巢狀結構，所以縮排不應該超過一到兩層，這樣函式會更容易閱讀和理解。

只做一件事

函式應該只做一件事，把這件事做好，而且只做這件事。

怎樣才算「一件事」？如果函式只做了函式名稱底下、同一層抽象概念的幾個步驟，就算只做了一件事。

  • 第一個範例混了兩層抽象概念（判斷是不是測試頁、組合 setup / teardown 的細節），可以再收縮重構。
  • 重構後的版本就很難再做有意義的收縮了。頂多把 if 搬進 includeSetupAndTeardownPages，但那只是換個方式重述原本的程式，沒有改變層次。

另一個判斷方法：看看你能不能從這個函式再提煉出一個新函式，而且新函式不只是把原本的實作換句話說。如果可以，這個函式就做了不只一件事。

每個函式只有一層抽象概念

要確定函式只做一件事，就要確定函式裡的敘述都在同一層抽象概念。

混合不同層次的抽象概念總是令人困惑，讀的人分不清某個表達式是基本概念還是細節。更糟的是，就像破窗效應，一旦細節和本質概念混在一起，就會有越來越多細節擠進這個函式。

由上而下閱讀：降層準則

程式碼應該像由上而下的敘事：每個函式後面，緊接著下一層抽象概念的函式。閱讀時就能順著一連串函式，一層一層往下讀，這就是降層準則。

這個技巧不容易學會，但非常重要：它是讓函式保持簡短、確保只做一件事的關鍵。

Switch 敘述

這個函式有幾個問題：

  1. 太長，而且每加一種員工型態就會更長
  2. 做了不只一件事
  3. 有不只一個理由需要修改它，違反單一職責原則（SRP）
  4. 新增型態時就必須修改它，違反開放封閉原則（OCP）
  5. 最糟的是，系統裡還會有無數個結構一模一樣的函式，例如 isPayday(Employee e, Date date)、deliverPay(Employee e, Money pay)

解法是把 switch 藏在 Abstract Factory 裡，不讓系統其他地方看到。Factory 用 switch 產生對應的物件，calculatePay、isPayday、deliverPay 則透過 Employee 介面以多型的方式分派：

可以容忍 switch 的條件：只出現一次、用來產生多型物件，而且藏在繼承關係底下，系統其他部分看不到。

使用具描述能力的名稱

  • 別怕名稱長。長但有描述性的名稱，比短但難懂的名稱好，也比一段長長的註解好。
  • 用一致的命名慣例，把幾個易讀的字詞組合起來，讓函式名稱自己說明意圖。
  • 別怕花時間取名。試幾個不同的名稱，放進程式裡讀讀看。現代 IDE（Eclipse、IntelliJ）讓改名變得很容易，換到你覺得夠有描述性為止。

函式的參數

參數越少越好：零個最好，其次一個，再來兩個，三個以上要有特殊理由。

  • 參數和函式屬於不同的抽象層次，參數會逼你去了解當下不重要的細節。
  • 從測試角度來看，要寫出涵蓋所有參數組合的測試案例非常困難，參數超過兩個時更是如此。

輸入型與輸出型參數

我們習慣「參數是輸入、回傳值是輸出」，很難預期函式會透過參數把結果傳出來，所以輸出型參數比輸入型參數難懂得多。

除了不用參數之外，只有一個輸入型參數的函式最好理解。例如 SetupTeardownIncluder.render(pageData)，一看就知道是要 render pageData。

單一參數的常見形式

  1. 詢問參數的問題，例如 boolean fileExists("MyFile")
  2. 轉換參數，然後回傳結果。轉換類的函式應該把結果當回傳值：StringBuffer transform(StringBuffer in) 比 void transform(StringBuffer out) 好懂。
  3. 事件（event）：比較少見但很有用。只有一個輸入參數、沒有輸出，用參數改變系統狀態，例如記錄密碼輸入失敗次數的 void passwordAttemptFailedNtimes(int attempts)。這種函式要讓讀者清楚知道它是一個事件，命名和上下文要特別謹慎。

旗標（Flag）參數

把 boolean 傳進函式是很糟的習慣。它讓方法簽名變複雜，等於大聲宣告「這個函式不只做一件事」：true 做 A，false 做 B。

看到 render(true) 會讓人困惑；滑鼠移過去看到 render(boolean isSuite) 稍微好一點，但還是不夠。應該拆成兩個函式：

兩個參數

兩個參數的函式比一個參數難懂，例如 writeField(name) 比 writeField(outputStream, name) 容易理解。

當然有時兩個參數很合理，例如 new Point(0, 0)：平面上的點本來就由兩個有序的值組成，看到 new Point(0) 反而會困惑。但 outputStream 和 name 並不是自然的組合，也沒有自然的順序。

即使像 assertEquals(expected, actual) 這樣常見的函式，兩個參數也沒有自然順序，要用久了才記得哪個在前。

能縮減成一個參數時，就該好好利用：

  • 把 writeField 變成 outputStream 的成員：outputStream.writeField(name)
  • 把 outputStream 變成類別的成員變數，就不用每次傳進方法
  • 建立新的 FieldWriter 類別，在建構子接收 outputStream，並提供 write 方法

三個參數

三個參數比兩個更難理解：順序、讀到時的停頓、被忽略的參數，這些問題都更嚴重。建立三個參數的函式之前要謹慎考慮。

例如 assertEquals(message, expected, actual)，常常要反覆查看才學會忽略 message。比較好的例子是 assertEquals(1.0, amount, .001)，用來檢查兩個浮點數在某個精確度下是否相等，三個參數的意義都很清楚。

動詞與關鍵字

好的函式名稱能解釋意圖，也能說明參數的順序。

  • 單一參數的函式，函式名稱和參數應該是動詞＋名詞的好搭配，例如 write(name)；writeField(name) 更好，進一步告訴我們 name 是一個 Field。
  • 關鍵字形式：把參數名稱寫進函式名稱。assertEquals 改成 assertExpectedEqualsActual(expected, actual)，就不用再記參數順序。

不要有副作用（Side Effect）

函式承諾只做一件事，卻偷偷做了別的事，就會產生副作用：可能意外改變同類別的其他變數，或把東西傳給其他函式、變成全域狀態，進而造成時序耦合（temporal coupling）和順序相依的問題。

例如 checkPassword 裡如果偷偷初始化了 session：

  • checkPassword：讀起來任何時間都可以呼叫
  • 實際上只能在初始化 session 的時機呼叫，否則會把現有的 session 清掉

如果真的要兩件事一起做，至少名稱要說清楚，例如 checkPasswordAndInitializeSession，雖然這樣仍然違反「只做一件事」。

避免輸出型參數

看到 appendFooter(s);，你會遲疑：是把 s 接到某個東西後面，還是把頁尾加到 s 後面？要看到宣告 public void appendFooter(StringBuffer report) 才能確定。

錯誤處理就是一件事

函式只做一件事，而錯誤處理本身就是一件事。所以處理錯誤的函式不應該再做別的事：如果函式裡有 try，它應該是函式的第一個字，而 catch / finally 之後不應該再有其他程式碼。

改用例外的話，新的例外從既有的例外類別衍生出來即可，不需要重新編譯和部署其他程式。

不要重複自己（DRY）

重複的程式碼可能是軟體中一切邪惡的根源，許多準則和慣例都是為了控制或消除重複而發明的：

  • 資料庫的 Codd 正規化，是為了消除資料的重複
  • 物件導向把程式碼集中到基礎類別，避免冗餘
  • 結構化程式設計、剖面導向（AOP）、元件導向程式設計，也都包含減少重複的策略

從副程式被發明以來，軟體開發的許多創新，都是在消除原始碼中的重複。

結構化程式設計

Dijkstra 的結構化程式設計準則：每個函式、函式中的每個區塊，都只有一個入口和一個出口。也就是只能有一個 return，迴圈裡不能有 break 或 continue，更不能有 goto。

這些準則在大型函式中好處很大。但如果函式保持簡短，偶爾出現多個 return、break 或 continue 並沒有壞處，有時甚至比單一入口 / 出口更有表達力。goto 只在大型函式中才有意義，應該避免。

開發函式的真實流程

沒有人一開始就能寫出這樣的函式。剛寫的時候，函式總是又長又複雜：很多縮排和巢狀迴圈、很長的參數串列、隨意的命名、重複的程式碼。但會有一整套單元測試，涵蓋每一行粗糙的程式碼。

接著開始琢磨和改善：拆分函式、重新命名、消除重複、縮短方法並調整順序，有時甚至拆開整個類別，同時一直保持單元測試通過。

最後，當函式符合本章的準則，才算完成。

總結

函式是程式語言裡的動詞，類別是名詞。照著這些準則，函式會簡短、命名良好、結構漂亮。但別忘了真正的目標：描述系統的故事。函式要整潔地組合在一起，形成清楚又精確的語言，幫你把這個故事說好。

Code Review 檢查清單

  • 三分鐘內看得懂這個函式在做什麼嗎？
  • 函式夠短嗎？理想 2～4 行，最多不超過 20 行
  • 縮排不超過一到兩層、沒有巢狀結構？
  • 只做一件事？所有敘述都在同一層抽象概念？
  • 函式由上而下排列，符合降層準則？
  • switch 只出現一次，並藏在 Factory 裡產生多型物件？
  • 名稱有足夠描述性，不需要看實作就知道它做什麼？
  • 參數不超過兩個？沒有 boolean 旗標參數、沒有輸出型參數？
  • 一組常一起出現的參數，已經包成物件？
  • 沒有隱藏的副作用？
  • 指令與查詢分開？
  • 用例外取代錯誤碼，try / catch 內容已提取成函式？
  • 沒有重複的程式碼？
