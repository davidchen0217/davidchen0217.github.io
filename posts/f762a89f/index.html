text 與 keyword

ElasticSearch 的字串有兩種類型：

textkeyword
存入時經過分詞（analyzer）：拆成 token、轉小寫整個字串原樣存成一個值
用途全文檢索（match）精確比對（term）、排序、聚合
例子文章內容、商品描述狀態碼、使用者 ID、email、標籤

使用 dynamic mapping（沒有事先定義 mapping）時，字串欄位預設兩種都建：

查全文用 title，排序或聚合用 title.keyword。兩種都做 indexing，會佔用比較多硬碟空間。所以正式環境建議先設計好 mapping，再寫入資料：只需要全文檢索的欄位用 text，只需要比對、聚合的欄位用 keyword。

時區：ElasticSearch 一律以 UTC 儲存

  • ElasticSearch 的日期一律以 UTC（+0）儲存，用日期命名的 index（例如 log-2021.10.01）也是依 UTC 的日期建立
  • 如果系統是台灣時間（UTC+8），用 Java Client 查詢時，要先把時間轉成 UTC 才能查到正確的資料
  • 也可以在 range 查詢裡指定時區，讓 ElasticSearch 幫你轉換：

例外：Kibana。Kibana 預設依照瀏覽器的時區顯示和查詢時間（dateFormat:tz 設定為 Browser），在台灣的電腦上就是 UTC+8，所以在 Kibana 上查詢不需要自己轉換。

基礎觀念筆記

搜尋

  • 查詢語言叫 Query DSL（Domain Specific Language）
  • query vs filter：query 會計算相關性分數、不快取；filter 只判斷符不符合，可以快取，效能較好
  • bool 查詢組合多個條件：must（必須符合）、filter（必須符合、不計分）、should（OR）、must_not
  • term 查詢相當於 SQL 的 WHERE 欄位 = 值；terms 相當於 IN (...)；range 適用數值和日期
  • fuzzy 查詢效能不好，盡量用其他方式取代
  • 自動完成、搜尋建議可以用 edge-ngram 分詞
  • Near real-time：寫入後預設約 1 秒（refresh interval）才搜尋得到；但用 _id 的 GET API 是即時的

Mapping

  • 舊版的 _type 已經移除，7.x 統一用 _doc，8.0 起不再支援帶 type 的 API
  • Mapping 不允許破壞性更新：已經存在的欄位不能改型態，只能新增欄位，或建新 index 再 reindex
  • 可以用 fields 替同一個欄位加上其他型態（multi-fields），例如 "fields": { "original": { "type": "keyword" } }
  • "_source": { "enabled": false }：不儲存原始文件，省空間，但查詢結果拿不到原始內容
  • doc_values: false：省硬碟空間，但這個欄位就不能排序和聚合

文件與 shard

  • Update 其實是刪除舊文件、重新 index 一份新的（delete + add）
  • _seq_no：index 裡每次異動遞增的序號；_primary_term：primary shard 每換一次就 +1。兩者一起用來做樂觀鎖
  • 單一 shard 建議不要超過約 50 GB（不是絕對），shard 數量要考慮叢集規模和資料量
  • Master-eligible node 可以被選為 master；voting-only node 只參與投票
  • 不要讓使用者直接存取 index，而是存取 alias，之後要換 index（例如 reindex）時才不用改程式

分頁

  • from + size 不能超過 index.max_result_window（預設 10000）
  • 原因是深度分頁很耗資源：每個 shard 都要回傳 from + size 筆給協調節點排序，頁數越後面越慢
  • 要取大量資料：Scroll API（建立快照，適合匯出）或 search_after（適合即時分頁），範例見這篇
  • 排序很耗記憶體

Bulk API

  • 格式是 NDJSON（每行一個 JSON 物件）
  • 建議從每次 1000～5000 筆、5～15 MB 開始測試，再依效能調整
