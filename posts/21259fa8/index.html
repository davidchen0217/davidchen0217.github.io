外觀模式（Facade）：替複雜的子系統提供一個簡單的介面，以及三個適用時機

發表於 2024-08-16 更新於 2026-11-27 分類於 ObjectOrientedProgramming 閱讀次數： Disqus： 文章字數： 1.8k 所需閱讀時間 ≈ 3 分鐘

這篇是《大話設計模式》外觀模式的讀書筆記：用一個 Facade 類別替好幾個子系統提供統一、簡單的介面，降低用戶端和子系統之間的耦合，並整理在設計初期、開發中、維護舊系統三個階段該如何運用外觀模式。

定義

外觀模式：為子系統中的一組介面提供一個一致的介面，此模式定義了一個高層介面，這個介面使得這一子系統更加容易使用。

它是迪米特法則的典型應用：用戶端只需要認識 Facade，不需要認識背後的每一個子系統。

基本結構

用戶端原本要自己知道「做 A 這件事要依序呼叫哪幾個子系統的哪幾個方法」，現在只要呼叫 MethodA()。

什麼時候使用

1. 設計初期：有意識地分層

例如經典的三層架構，在資料存取層（DAO）、商業邏輯層（BO）、展示層之間建立 Facade，替複雜的子系統提供簡單的介面，大幅降低層與層之間的耦合。

2. 開發階段：子系統越來越複雜

子系統經過不斷重構和演化，會產生很多很小的類別。這本來是好事（每個類別職責單一），但也讓使用它們變得麻煩。加一個 Facade 提供簡單的介面，可以減少使用者和這些小類別之間的依賴。

3. 維護遺留系統

維護一個很難修改和擴充的大型舊系統時，可以替新系統開發一個 Facade 類別：

  • Facade 替設計粗糙或高度複雜的舊程式碼，提供一個比較清楚的介面
  • 新系統只和 Facade 互動
  • Facade 負責和舊程式碼打交道，處理所有複雜的工作

這也是逐步汰換舊系統（Strangler 模式）時常用的手法。

實務上的例子

  • SLF4J 的名字就是 Simple Logging Facade for Java：程式只認識 SLF4J，背後可以是 Logback 或 Log4j2
  • 微服務架構裡的 API Gateway / BFF（Backend for Frontend）：前端只呼叫一個入口，由它去整合背後的多個服務
