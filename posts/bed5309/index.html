YAML 撰寫注意事項

Filebeat 的設定檔是 YAML，格式錯一點就會無法啟動：

  1. 大小寫有差別
  2. 用縮排表示階層關係
  3. 縮排只能用空白，不能用 Tab
  4. 縮排幾個空白不重要，只要同一層的元素左邊對齊即可

常見錯誤排解

Filebeat error loading config file: yaml: did not find expected key

情境：啟動 Filebeat 後，ps -ef | grep filebeat 找不到 process。查看 logs 出現：

原因：yml 設定檔裡有 Filebeat 不認得的格式或字元。我們遇到的是編輯 yml 時不小心多打了一個特殊字元，也常見於縮排用了 Tab 或沒對齊。

解法：錯誤訊息通常會指出是哪一個 yml 有問題，修正後可以用 filebeat test config -c custom.yml 先驗證設定檔再啟動。

nohup: failed to run command ‘./filebeat’: Permission denied

原因：filebeat 執行檔沒有執行權限，常發生在用 binary 解壓縮或從別處複製過來時。

logs 裡出現 ERROR，但看不出原因

/logs/filebeat 出現 ERROR，但訊息看不出原因。我們遇過的兩種情況：

  1. 硬碟滿了：log 只寫了一半，導致 parse 錯誤
  2. log 的格式和 yml 設定的欄位不一致：無法 mapping

對應的預防方式：

  1. 替 Server 設定硬碟空間告警，超過 80% 就通知相關人員
  2. 所有透過 Filebeat 送出的 log，統一控管格式

log 被重新推送

有兩種情況會讓 Filebeat 把舊的 log 重新推一次：

  1. AWS EBS 從 gp2 升級到 gp3：底層可能換成全新的主機或磁碟
  2. 用 mv 把 log 搬到不同位置

原因是 Filebeat 在 registry 裡用檔案的 inode 和 device ID 記錄每個檔案讀到哪裡。磁碟換了，或檔案搬到另一個檔案系統，識別值就變了，Filebeat 會把它當成新檔案從頭讀起。遇到這類維運操作前，要先確認下游能不能接受重複的 log，或預先調整 ignore_older。

補充：新版 Filebeat

這篇的設定以 Filebeat 7.x 為主。新版 Filebeat 推出了 filestream input，log input 從 7.16 起已標為 deprecated，新專案建議改用 filestream。
