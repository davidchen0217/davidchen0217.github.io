Clean Code 註解：什麼註解該寫、什麼註解該刪（完整筆記）

發表於 2024-08-17 更新於 2026-11-26 分類於 CleanCode 閱讀次數： Disqus： 文章字數： 7.3k 所需閱讀時間 ≈ 13 分鐘

這篇是《Clean Code》第 4 章「註解」的完整閱讀筆記：為什麼註解是「必要之惡」、哪 8 種註解值得寫、哪 17 種註解應該刪掉，每一種都附上範例，最後整理成一份 Code Review 時可以直接用的檢查清單。

註解是必要之惡

在最好的情況下，註解也只是一種必要之惡。如果程式語言的表達力足夠，也許根本不需要註解。

適當使用註解，是為了彌補我們沒能用程式碼表達意圖的失敗。所以每次想寫註解時，先想一想：有沒有辦法直接用程式碼表達？

註解會說謊

註解存在得越久，就越可能偏離它當初解釋的程式碼，甚至完全誤導。原因很簡單：工程師沒有確實維護它。

程式碼會被修改、演化，區塊會被搬來搬去、拆開、複製、重新組合，但註解沒辦法每次都跟著移動。結果常常看到註解和它原本要解釋的程式碼分開，變成孤零零的段落，越來越不準確。

所以請把力氣花在讓程式碼更清楚，從一開始就不需要註解。真相只存在一個地方：程式碼。只有程式碼能忠實告訴你它做了什麼。

註解無法彌補糟糕的程式碼

寫註解常見的動機，是程式寫得太糟。我們知道這個模組又亂又難懂，於是告訴自己：「最好幫它寫個註解！」這是錯的，最好的做法是把它整理乾淨。

整潔、有表達力、幾乎不需要註解的程式碼，遠勝過雜亂複雜、滿是註解的程式碼。與其花時間寫註解解釋自己造成的混亂，不如花時間整理它。

大部分想寫在註解裡的意圖，都可以直接變成函式名稱。

好的註解

有些註解是必要或有益的。但要記得：真正好的註解，是你想辦法不寫的註解。

1. 法律型註解

壞的註解

大部分註解都屬於這一類。它們通常是爛程式碼的藉口、為糟糕決定找理由，或者只是工程師在自言自語。

1. 喃喃自語（Mumbling）

想寫就寫，或只因為流程要求就寫一個註解，這是亂寫。如果決定要寫，就要花必要的時間寫出最好的註解。

catch 裡的註解是什麼意思？大概是發生 IOException 代表找不到屬性檔，這時會載入所有預設值。但中間還有好幾種可能，唯一的辦法是去翻系統其他部分的程式碼才知道到底發生什麼事。逼讀者去看其他模組才能懂的註解，就是失敗的註解。

2. 多餘的註解

這個註解沒有提供比程式碼更多的資訊，沒有說明意圖或理由，讀它可能比讀程式碼還久，而且比程式碼更不精確。

3. 誤導型註解

同一個例子，註解其實還寫錯了：this.closed 變成 true 時，這個方法並不會立刻返回。它只在一開始檢查 closed 是不是 true；否則會盲目等待一段時間，時間到了如果 closed 還不是 true，就丟出例外。

這種細微的錯誤藏在註解裡，可能讓其他工程師放心地呼叫它，以為 closed 一變成 true 就會馬上返回。

9. 位置標誌

在極少數情況下，用這種橫幅把某些函式集中起來是合理的。但通常它們只是雜物，應該刪掉，尤其是尾巴那一長串斜線。

如果很少使用，橫幅反而會很醒目；用太多，就會變成被忽略的背景。只在效果非常顯著時才用。

10. 右大括號後的註解

對很長、巢狀很深的函式也許有意義，但我們偏好短小的函式，這種註解只會造成凌亂。覺得需要在右大括號後加註解時，應該做的是把函式改短。

11. 出處及署名

版本控制系統已經記錄了每一行是誰、在什麼時候加的，不需要用署名汙染程式碼。你可能覺得這樣方便知道該找誰討論，但這種註解放久了只會越來越不準確。這類資訊交給版本控制系統。

12. 被註解掉的程式碼

其他人看到被註解掉的程式碼，會不敢刪：「留著一定有原因，一定很重要。」於是這些程式碼就像壞掉的葡萄酒瓶底的沉澱物，越積越多。

以前被註解掉的程式碼也許有參考價值，但現在有版本控制系統幫我們記住歷史。直接刪掉，不會弄丟的。

13. HTML 註解

原始碼裡的 HTML 註解很討人厭，讓本來好讀的註解變得難讀。如果註解要被 Javadoc 之類的工具轉成網頁，加上 HTML 修飾是工具的責任，不是工程師的責任。

14. 非區域性的資訊

註解只應該描述附近的程式碼，不要在區域性的註解裡提供系統的全域資訊：

這個函式根本不控制預設值，註解描述的是系統裡另一個很遠的地方。一旦那邊的預設值改了，這裡的註解不會有人記得改。

15. 過多的資訊

不要把有趣的歷史討論或無關的細節放進註解。例如一個測試 base64 編解碼的模組，開頭貼了一大段 RFC 2045（MIME）的規格內容。讀程式的人除了 RFC 編號以外，根本不需要那些難懂的資訊。

16. 不明顯的關聯

註解和它描述的程式碼之間，關聯應該很明顯：

讀的人要能看出註解和這行運算的關係才看得懂。註解的目的是解釋程式碼無法自我表達的部分，如果註解本身還需要解釋，就很遺憾了。

17. 非公共程式碼的 Javadoc

Javadoc 對公共 API 很有幫助，但對不打算公開的程式碼就不是這樣了。替系統內部的每個類別和函式產生 Javadoc 頁面，通常只會因為格式要求而產生一堆無關的內容，分散注意力。

註解檢查清單

寫註解之前：

  • 能不能改用函式名稱或變數名稱表達？
  • 能不能把程式整理乾淨，讓註解變得不需要？

保留的註解：

  • 屬於好的註解：法律、資訊、意圖、闡明、後果告誡、TODO、放大重要性、公共 API Javadoc？
  • 內容正確，而且和程式碼一致？
  • 只描述附近的程式碼，和程式碼的關聯一看就懂？

應該刪掉的註解：

  • 重述程式碼、規定才寫的 Javadoc、getter / setter 上的干擾型註解
  • 修改日誌、作者署名（交給版本控制）
  • 被註解掉的程式碼
  • 右大括號後的註解（改成把函式寫短）
  • 位置標誌橫幅、HTML 標籤、大段的規格或歷史討論
  • 定期清理已經完成或不需要的 TODO
