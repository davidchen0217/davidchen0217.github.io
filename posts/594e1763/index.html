Developing on AWS 課程筆記：IAM、S3、DynamoDB、Lambda、API Gateway 與微服務架構

發表於 2022-10-11 更新於 2026-11-26 分類於 AWS 閱讀次數： Disqus： 文章字數： 6.5k 所需閱讀時間 ≈ 12 分鐘

這篇是我上 AWS 官方「Developing on AWS」三天課程的筆記整理：第一天是 SDK / CLI、IAM 權限與 S3；第二天是 DynamoDB（含 RCU 計算）、Lambda 與 API Gateway；第三天是微服務拆分、Cognito 驗證、Step Functions 與可觀測性。課堂上講到的重點和考試常考的觀念都整理在這裡。

Day 1：SDK、IAM 與 S3

AWS SDK 與 CLI

SigV4 簽章與時間戳記

AWS API 請求都用 Signature Version 4（SigV4） 簽章。簽章裡包含時間戳記，AWS 會拒絕時間差太多的請求，用來防止重送攻擊（replay attack）。所以呼叫 AWS API 的機器一定要做好對時，時間不準會直接導致簽章驗證失敗。

使用 SDK 要注意的事

  • 很多操作是非同步的：例如建立 S3 bucket、建立 DynamoDB table，API 回傳成功不代表資源已經可以用，要檢查狀態。SDK 有提供 waiter，可以等到資源就緒再繼續
  • 分頁（Pagination）：例如 DynamoDB 的 Query / Scan 每次最多回傳 1 MB，超過要用回傳的 LastEvaluatedKey 繼續查；SDK 提供 paginator 幫你處理
  • 自動重試：各語言的 AWS SDK 都內建重試邏輯，遇到節流（Throttling）等暫時性錯誤會自動以退避（backoff）方式重試，次數依 SDK 和重試模式而定
  • Low-level API 要自己關閉連線；高階的 client API 則提供更高一層的抽象，處理掉很多細節
  • 可以把 while 迴圈之類的重複邏輯包成 wrapper 方法，讓呼叫端更簡潔
  • 搭配 APM（Application Performance Monitoring）工具觀察 API 呼叫的延遲和錯誤

CLI 小技巧

IAM：驗證、授權與稽核

3A

意義AWS 服務
Authentication（驗證）你是誰IAM
Authorization（授權）你能做什麼IAM
Accounting（稽核）你做了什麼CloudTrail

ARN（Amazon Resource Name）

AWS 用 ARN 唯一識別每個資源：

  • partition：一般區域是 aws（另有中國區 aws-cn、美國政府區 aws-us-gov）
  • region：例如 us-west-2、ap-northeast-1
  • account-id：12 位數的帳號 ID
  • resource：資源名稱，可以用 * 萬用字元

例如 DynamoDB table：arn:aws:dynamodb:ap-northeast-1:123456789012:table/Orders。S3 bucket 名稱是全域唯一的，所以它的 ARN 省略 region 和 account：arn:aws:s3:::my-bucket。

兩種政策

Identity-based policy：掛在使用者、群組或 role 上，描述「這個身分能做什麼」：

元素必要
Effect（Allow / Deny）必要
Action必要
Resource必要
Condition選用

Resource-based policy：掛在資源上（例如 S3 bucket policy），描述「誰能對這個資源做什麼」，所以多了 **Principal**（誰）。考試常考的就是判讀這種政策。

S3 的權限要分清楚兩個層級：bucket 層級的動作（例如 s3:ListBucket，Resource 寫 bucket ARN）和物件層級的動作（例如 s3:GetObject，Resource 寫 bucket/*）。

權限評估規則

  1. 預設一律拒絕（implicit deny）
  2. 有 Allow 才允許
  3. 只要有任何明確的 Deny，就一定拒絕：Allow 和 Deny 衝突時，Deny 優先

Permission boundary（權限邊界）：替身分設定「最多能有哪些權限」的上限。實際生效的權限是 identity policy 和 permission boundary 的交集。

用 Role，不要每個系統開一個 IAM 使用者

  • 不建議替每個系統開一個 IAM 使用者帳號，改用 Role
  • 角色型存取控制：一個人同一時間只扮演一個 role，例如從 developer 切換到 QA 時 assume role，做完再切回來，避免同時擁有多個身分而誤操作
  • 在 EC2 上，用 instance profile 掛 role，程式透過 STS 自動取得暫時憑證，不要把 Access Key / Secret Key 寫在機器上

儲存服務

服務類型說明
EBS區塊儲存掛在 EC2 上的磁碟；Provisioned IOPS 類型可以保證 IOPS
EFS檔案儲存（NFS）給 Linux 共用的網路檔案系統；有 Standard 和較便宜的 Infrequent Access 類別
FSx for Windows File Server檔案儲存（SMB）給 Windows 用的共用檔案系統
FSx for Lustre平行檔案系統高效能運算（HPC）、機器學習等大量平行讀寫
S3物件儲存下面詳述

S3

基本觀念

  • S3 是 AWS 全代管的服務
  • 物件由 key（完整路徑）、資料內容、metadata 組成
  • 沒有真正的資料夾：Dev/a.txt 只是 key 剛好有 Dev/ 這個 prefix，主控台用 /（delimiter）把它顯示成資料夾
  • 存取網址：https://{bucket}.s3.{region}.amazonaws.com/{key}
  • bucket 名稱全域唯一，但建立時要指定 region
  • 有 Dualstack endpoint，同時支援 IPv4 和 IPv6
  • HeadBucket / HeadObject 只取 metadata，不下載內容

儲存類別

類別說明
S3 Standard資料複製到至少 3 個 AZ，耐久度 99.999999999%（11 個 9）
S3 Standard-IA不常存取但需要立即讀取的資料，儲存費用較低、讀取要付費
S3 One Zone-IA只存在單一 AZ，更便宜，但 AZ 故障時資料可能遺失
S3 Intelligent-Tiering自動依存取頻率搬移：30 天沒被存取就自動移到不常存取層
S3 Glacier封存用，像磁帶備份，取回需要時間

版本控制

  • 預設關閉，關閉時上傳同名物件會直接覆蓋
  • 一旦開啟就無法關閉，只能暫停（suspend）
  • 開啟後刪除物件，其實是插入一個 delete marker，舊版本仍然保留

上傳大型檔案

  • 單次 PUT 上傳最大 5 GB
  • Multipart upload：先初始化取得 UploadId，再分段上傳，每段 5 MB～5 GB，最多 10,000 段，單一物件最大 5 TB
  • AWS 建議超過 100 MB 的檔案就使用 multipart upload；它也支援續傳，某一段失敗只要重傳那一段

其他功能

  • Presigned URL：產生有期限的網址，讓沒有 AWS 憑證的人也能在時效內上傳或下載特定物件
  • 列表分頁：ListObjectsV2 回傳 IsTruncated: true 代表還有下一頁
  • S3 Select：對 CSV、JSON 等半結構化檔案下 SELECT ... FROM ... WHERE 只取部分資料（不支援 GROUP BY）。注意：AWS 已在 2024 年停止對新客戶提供 S3 Select
  • S3 Batch Operations：對大量物件批次執行複製等操作
  • CORS：網頁要從其他網域直接存取 bucket 時，要在 CORS 設定 AllowedOrigin
  • S3 Access Points：替同一個 bucket 建立多個各自有權限設定的存取點

Day 2：DynamoDB、Lambda 與 API Gateway

從 SQL 到 NoSQL

  • SQL 是 schema on write（寫入時就要符合結構），NoSQL 多是 schema on read
  • NoSQL 是為了解決單一節點的擴展瓶頸，雲端的優勢在於水平擴展
  • CAP 定理：一致性（Consistency）、可用性（Availability）、分區容錯（Partition tolerance）三者無法同時滿足
  • 最終一致性：資料寫入後，經過一段時間最終會一致

DynamoDB

基本觀念

關聯式資料庫DynamoDB
TableTable
RowItem
ColumnAttribute
  • 個位數毫秒的低延遲查詢
  • 單一 item 最大 400 KB
  • Primary key = Partition key（必要，key schema 裡叫 HASH）+ Sort key（選用，叫 RANGE）
  • Partition key 要選高基數（high cardinality）、分布平均的值，例如 UUID、流水號，避免資料都擠在同一個 partition
  • Control plane 是管理表格的操作（像 DDL，例如 CreateTable）；Data plane 是讀寫資料的操作（像 DML，例如 PutItem、Query）

讀取一致性與 RCU 計算

強一致性讀取最終一致性讀取
1 RCU 可以做到每秒 1 次、最多 4 KB 的讀取每秒 2 次、最多 4 KB 的讀取

計算方式：每次讀取的 item 大小除以 4 KB 並無條件進位，再乘上每秒讀取次數。

情境強一致性最終一致性
每秒 10 次讀取、每個 item 8 KB10 × (8 ÷ 4) = 20 RCU20 ÷ 2 = 10 RCU
每秒 10 次讀取、每個 item 14 KB10 × ⌈14 ÷ 4⌉ = 10 × 4 = 40 RCU40 ÷ 2 = 20 RCU

寫入則是 1 WCU = 每秒 1 次、最多 1 KB 的寫入。

Burst capacity：DynamoDB 會保留最多 5 分鐘沒用完的容量，應付短暫的流量高峰。

索引

GSI（Global Secondary Index）LSI（Local Secondary Index）
Partition key可以和主表不同必須和主表相同
Sort key可以不同不同
容量有自己的 RCU / WCU和主表共用
建立時機隨時可以建立只能在建立 table 時建立

索引本質上是把資料另外複製一份，用不同的 key 組織。

操作重點

  • BatchWriteItem 一次最多 25 個 item，可以把資料準備成 JSON 檔再用 CLI 匯入
  • GetItem 要提供完整的 primary key：有 sort key 的表也要帶 sort key
  • Query / Scan 一次最多回傳 1 MB，超過要分頁
  • Parallel scan：把 table 切成多個 segment 平行掃描，概念類似 MapReduce
  • DAX：DynamoDB 前面的記憶體快取，讀取延遲可以降到微秒等級
  • Java SDK 建議使用高階的 Object Persistence Interface（例如 DynamoDB Mapper / Enhanced Client），直接對應 Java 物件
  • NoSQL Workbench：設計 DynamoDB 資料模型的桌面工具

Lambda

重要限制

項目限制
最長執行時間15 分鐘
部署套件zip 直接上傳 50 MB；解壓縮後 250 MB
Layers每個函式最多 5 個
同時執行數每個 region 預設 1,000（可申請提高）

更大的程式可以打包成容器映像檔，放在 Amazon ECR（AWS 版的 Docker Hub）。

觀念

  • Event source 觸發 Lambda，需要授予它 invoke 的權限
  • 處理函式會收到 event（上游傳來的資料）和 context（執行環境的資訊，例如剩餘時間）
  • 執行環境會被重複使用，全域變數可能在多次呼叫之間保留；重新部署後就會重置
  • 冷啟動（cold start）：執行環境第一次建立時比較慢。可以用 Provisioned Concurrency 預先暖機
  • 不要把 Lambda 當 EC2 用：它適合短時間、事件驅動的工作，不適合長時間常駐的服務
  • 共用的函式庫可以做成 Layer

API Gateway

  • 面對外部使用者（customer facing）的 API 入口
  • HTTP API：較簡單、便宜，適合單純轉發；REST API：功能完整（API key、使用量方案、請求驗證等）
  • 支援匯入 Swagger / OpenAPI 定義
  • 支援金絲雀發布（Canary release）：先把一小部分流量導到新版本

Day 3：微服務、Cognito 與 DevOps

從單體到微服務

  • 單體（Monolith） 的問題：一處修改影響全部，部署和擴展都綁在一起
  • 微服務要切多細？組織的架構決定系統的邊界（康威定律）
  • Domain-Driven Design（DDD）：每個服務都從業務領域（domain）切入，服務之間透過 API 溝通
  • 新創初期不適合 DDD：人力配置不完整，花時間；而且領域通常變化很快，邊界還不穩定

從單體遷移的模式

  • Strangler（扼殺者）模式：在舊系統外面包一層，把功能一個一個搬到新服務，逐步取代舊系統，而不是一次重寫
  • Anti-corruption layer（防腐層）：新舊系統之間的轉換層，把舊系統的資料模型和介面轉成新系統的語言，避免舊系統的設計「汙染」新服務
  • Facade（外觀）模式：對外提供單一、簡化的介面，隱藏背後多個服務

Step Functions

用來編排（orchestrate）多個 Lambda 或 AWS 服務的工作流程：

  • 避免 Lambda 直接 invoke 另一個 Lambda，形成難以追蹤、甚至無限迴圈的呼叫鏈
  • 用 Step Functions 內建的 retry 取代自己寫迴圈重試

Cognito：使用者驗證

為什麼需要 Cognito？它幫應用程式處理驗證（Authentication）和授權（Authorization），不用自己實作註冊、登入、密碼重設：

  • User pool：使用者目錄，負責註冊和登入。登入成功後回傳 JWT（ID token、Access token、Refresh token）
  • Identity pool：把登入的使用者換成暫時的 AWS 憑證，讓前端可以直接呼叫 AWS 服務

ID token 解碼後的常見欄位：

欄位意義
iss發行者，也就是哪一個 User pool
aud對象，也就是 App client ID
sub使用者的唯一 ID
cognito:username使用者名稱
token_useid 或 access
auth_time、iat、exp驗證時間、發行時間、到期時間

後端收到 JWT 後，要驗證簽章、iss、aud 和 exp，才能信任裡面的資訊。

另外別搞混：AK / SK（Access Key ID / Secret Access Key）是 AWS 的長期程式存取憑證，和使用者登入用的 JWT 是不同的東西。

DevOps 與可觀測性

  • DevOps：開發（Development）和維運（Operations）一起合作的文化，重點是標準化和自動化
  • Infrastructure as Code（IaC）：用程式碼定義基礎設施，例如 CloudFormation、AWS CDK
  • 可觀測性（Observability）三大支柱：Logging（日誌）、Metrics（指標）、Tracing（分散式追蹤，例如 AWS X-Ray）
  • EventBridge：事件匯流排，讓服務之間用事件解耦
