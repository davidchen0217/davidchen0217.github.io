工廠方法模式與抽象工廠模式：切換資料庫的範例、優缺點，以及用反射和設定檔去除 switch

發表於 2024-09-11 更新於 2026-11-27 分類於 ObjectOrientedProgramming 閱讀次數： Disqus： 文章字數： 3k 所需閱讀時間 ≈ 5 分鐘

這篇是《大話設計模式》工廠方法模式與抽象工廠模式的讀書筆記：工廠方法如何把「建立哪個產品」交給子類別、抽象工廠如何一次建立一整個系列的產品（以同時支援 SQL Server 和 Access 的資料存取為例）、抽象工廠的優缺點，以及用反射加設定檔取代工廠裡的 switch。

工廠方法模式（Factory Method）

簡單工廠把所有判斷都放在一個工廠類別裡，每新增一種產品就要修改工廠的 switch，違反開放封閉原則。

工廠方法模式改成：定義一個建立物件的介面，讓子類別決定要實體化哪一個類別。每種產品都有自己的工廠：

要改成志工來幫忙，只要把 UndergraduateFactory 換成 VolunteerFactory；新增一種產品，只要新增一組產品類別和工廠類別，不用修改既有的程式。

缺點是：每多一種產品就多一個工廠類別，增加了額外的開發量；判斷用哪個工廠的邏輯，也移到了用戶端。

抽象工廠模式（Abstract Factory）

情境：同時支援多種資料庫

同一個專案要支援 SQL Server 和 Access，而且有好幾張表（User、Department）。這是多個產品系列的問題：

結構

  • IFactory 是抽象工廠介面，包含所有產品的建立方法
  • SqlServerFactory、AccessFactory 是具體工廠，各自建立同一個系列的產品
  • 通常在執行期間才建立具體工廠的實體；要建立不同系列的產品，就使用不同的具體工廠

優點

  1. 容易切換產品系列：只要換一個具體工廠，就能使用整組不同的產品
  2. 建立過程和用戶端分離：用戶端透過抽象介面操作，具體的產品類別名稱完全不會出現在用戶端程式碼

缺點

新增一種產品很痛苦。例如要新增一張 Project 表，就要新增 IProject、SqlServerProject、AccessProject，還要修改 IFactory、SqlServerFactory、AccessFactory，牽一髮而動全身。

**所有用到簡單工廠的地方，都可以考慮用反射去除 switch 或 if**，解除分支判斷帶來的耦合。現代的依賴注入框架（例如 Spring、.NET 的 DI container）本質上也是用設定加反射來決定要建立哪個實作。
