狀態模式（State）：用類別取代一長串的狀態判斷，以「工作狀態」範例說明與優缺點

發表於 2024-09-28 更新於 2026-11-27 分類於 ObjectOrientedProgramming 閱讀次數： Disqus： 文章字數： 3.1k 所需閱讀時間 ≈ 6 分鐘

這篇是《大話設計模式》狀態模式的讀書筆記：從「方法過長是壞味道」開始，說明當一個物件的行為取決於它的狀態、而狀態判斷的 if / else 越寫越長時，如何把每個狀態拆成一個類別；接著是狀態模式的基本結構、「一天的工作狀態」範例，以及優缺點和使用時機。

起點：方法過長是壞味道

Martin Fowler 在《重構》中提到一個很重要的程式碼壞味道：Long Method（方法過長）。方法很長，往往代表它承擔了太多責任。

最典型的例子是一大段依狀態分支的程式：

物件導向設計希望做到的是責任分解：把這些分支一個一個變成類別，新增狀態時不會影響其他類別，狀態的變化也在各自的類別中完成。GoF 提供的解決方案就是狀態模式。

定義

狀態模式：當一個物件的內在狀態改變時允許改變其行為，這個物件看起來像是改變了其類別。

主要解決的是：控制一個物件狀態轉換的條件判斷過於複雜的情況。把狀態的判斷邏輯轉移到表示不同狀態的一系列類別中，就能把複雜的判斷邏輯簡化。

範例：一天的工作狀態

每個狀態只處理自己的時段，不屬於自己的就交給下一個狀態。

需求變更：公司規定員工必須在 20 點之前離開。只要新增一個「強制下班」狀態，並修改傍晚工作狀態的判斷，其他狀態的程式碼完全不用動。

優點

  • 把與特定狀態相關的行為局部化，不同狀態的行為被分割在不同的類別
  • 所有和某個狀態相關的程式碼都在對應的 ConcreteState 裡，新增狀態和轉換只要新增子類別
  • 消除龐大的條件分支：大型的分支判斷難以修改和擴充，就像早期的雕版印刷，任何改動都要整版重刻。狀態模式把狀態轉移邏輯分散到各個 State 子類別之間，減少彼此依賴

缺點

  • 狀態很多時，類別數量也會跟著變多
  • 狀態轉換的邏輯分散在各個狀態類別中，要了解完整的流程，必須看過每個類別

什麼時候使用

當一個物件的行為取決於它的狀態，而且必須在執行期間根據狀態改變它的行為時，就可以考慮使用狀態模式。常見的例子有訂單狀態（待付款、已付款、已出貨、已完成、已取消）、工作流程審核、遊戲角色狀態、TCP 連線狀態等。
