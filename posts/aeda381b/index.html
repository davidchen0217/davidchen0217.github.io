觀察者模式（Observer）：發佈 / 訂閱的基本結構、特點與不足，以及用 C# 事件委託改寫

發表於 2024-08-26 更新於 2026-11-27 分類於 ObjectOrientedProgramming 閱讀次數： Disqus： 文章字數： 2.9k 所需閱讀時間 ≈ 5 分鐘

這篇是《大話設計模式》觀察者模式的讀書筆記：觀察者模式（又叫發佈 / 訂閱模式）的基本結構、它如何解除通知者和觀察者之間的耦合、觀察者模式的不足（觀察者還是得實作同一個介面），以及如何用 C# 的事件委託（delegate / event）解決這個問題。

定義

觀察者模式定義了一種一對多的依賴關係，讓多個觀察者物件同時監聽某一個主題物件。這個主題物件在狀態發生變化時，會通知所有觀察者物件，使它們能夠自動更新自己。

基本結構

特點

  • 使用時機：一個物件改變時，需要同時改變其他物件，而且不知道具體有多少物件需要改變
  • 觀察者模式做的事情就是解除耦合：讓耦合的雙方都依賴於抽象，而不是依賴於具體，各自的變化都不會影響另一邊
  • 實務上，具體的觀察者很可能是毫不相關的類別，它們只是都需要在收到通知時做 Update()，所以讓它們實作同一個介面最合適：

觀察者模式的不足

雖然用了依賴倒轉，但抽象的通知者還是依賴抽象的觀察者：沒有 IObserver 這個介面，通知功能就做不出來。

而且每個具體觀察者被通知時，不一定都是呼叫 Update()。例如老闆回來了，看股票的同事要「關閉股票程式」，看球賽的同事要「關閉球賽轉播」，方法名稱和功能都不一樣。

如果通知者和觀察者根本互相不知道對方，由用戶端決定通知誰、呼叫哪個方法，就能解決這個問題。

用事件委託改寫

委託是什麼

委託（delegate）是一種參考方法的型別：

  • 一旦替委託指定了方法，委託就會和那個方法有完全相同的行為，可以像一般方法一樣有參數和回傳值
  • 可以把委託看成對函式的抽象，是「函式的類別」，委託的實例代表一個具體的函式
  • 一個委託可以掛載多個方法，呼叫時會依序執行
  • 掛載的方法不需要屬於同一個類別
  • 前提是所有掛載的方法都要有相同的簽章（相同的參數列表和回傳型別）

改寫

Boss 完全不知道有哪些觀察者，觀察者也不需要實作任何共同介面，方法名稱可以各自不同。

實務上的例子

  • C# 的 event、Java Swing 的 ActionListener、瀏覽器的 addEventListener
  • 應用程式內的事件匯流排（例如 Spring 的 ApplicationEventPublisher）
  • 跨服務的訊息佇列 Pub/Sub（Redis Pub/Sub、Kafka），可參考 Redisson 的 Pub/Sub
