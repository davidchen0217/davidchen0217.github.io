Redis 基礎與 Key 設計規範：常用資料結構、Key 命名、避免 bigkey、Docker 安裝與主從複製

發表於 2020-07-27 更新於 2026-11-27 分類於 Redis 閱讀次數： Disqus： 文章字數： 2.8k 所需閱讀時間 ≈ 5 分鐘

這篇整理使用 Redis 的基礎筆記：常用資料結構與指令的時間複雜度、Key 和 Value 的設計規範（命名、長度、避免 bigkey、設定過期時間）、哪些指令不要在正式環境使用、String 和 Hash 的大小上限、用 Docker 安裝 Redis 的設定檔，以及主從複製（Replication）的用途。

常用資料結構與指令

指令資料結構時間複雜度說明
INCR / INCRBY key nStringO(1)把數值加 1 / 加 n，回傳新值。key 不存在時從 0 開始。數值範圍是 64 位元有號整數，常用來做計數器
HSET key field value [field value ...]HashO(N)設定 hash 的一個或多個欄位，N 是欄位數。舊的 HMSET 從 Redis 4.0 起已被 HSET 取代
SPOP keySetO(1)隨機取出並移除一個元素；只想隨機取、不想移除用 SRANDMEMBER
LPUSH / RPUSH key valueListO(1)LPUSH 加到 list 開頭，RPUSH 加到結尾。key 存在但不是 list 時會回傳錯誤
LLEN keyListO(1)回傳 list 長度，key 不存在回傳 0

大小上限

  • String 的值最大 512 MB，key 本身也最大 512 MB
  • 一個 Hash 最多 2³² − 1 個欄位（超過 40 億）
  • 上限很大，但不代表應該放這麼大，見下面的 bigkey

Key 設計規範

命名

  • 可讀、可管理：以業務名稱（或資料庫名稱）當前綴避免衝突，用冒號分隔，例如 業務名:表名:id
    • u200taiwan → userid:200:taiwan
  • 固定格式：用 : 分隔層級，多個字組成一個詞時用 . 或 -，例如 userid:200:taiwan:father-man
  • 簡潔：在語意清楚的前提下控制長度。key 很多時，長度會直接影響記憶體用量
  • 不要用特殊字元：空白、換行、單雙引號等

長度

  • 不建議使用非常長的 key，例如 1024 bytes 的 key，比較時耗時、也浪費記憶體
  • 如果真的需要用很長的內容當 key，可以改用它的雜湊值

Value 設計

1. 拒絕 bigkey

  • String 類型盡量控制在 10 KB 以內
  • Hash、List、Set、ZSet 的元素個數盡量不超過 5000
  • 反例：一個包含 200 萬個元素的 List

bigkey 會讓單一指令執行很久，而 Redis 是單執行緒的，會阻塞其他所有請求。刪除非字串類型的 bigkey 時不要直接 DEL，改用 HSCAN、SSCAN、ZSCAN 分批刪除，或使用 UNLINK（Redis 4.0 起，在背景刪除）。也要注意 bigkey 過期被自動刪除時同樣會造成阻塞。

可以用 redis-cli --bigkeys 找出目前最大的 key。

指令使用規範

  1. O(N) 指令要注意 N 的大小：HGETALL、LRANGE、SMEMBERS、ZRANGE、SINTER 不是不能用，但要確定 N 有多大。需要走訪時，改用 HSCAN、SSCAN、ZSCAN
  2. 正式環境禁用的指令：KEYS、FLUSHALL、FLUSHDB。可以用 rename-command 把它們改名或停用，需要找 key 時用 SCAN
  3. 批次操作提高效率：原生的 MGET、MSET，或用 pipeline 一次送多個指令。一次批次的元素數量也要控制，例如 500 個以內（實際還要看每個元素的大小）

主從複製（Replication）

依照 Redis 官方文件，Replication 是 Master-Slave 模式的複製機制：slave 會成為 master 的完整複本。用途有兩個：

1. 讀寫分離

master 負責寫入，多個 slave 分攤讀取的壓力，例如把很慢的 O(N) 查詢丟給 slave 執行。

2. 高可用

master 掛掉時，把其中一個 slave 升級成新的 master，達成故障轉移（failover）。搭配 Redis Sentinel 可以自動完成這件事。

要注意複製是非同步的：master 寫入成功後才會同步給 slave，所以 slave 的資料可能稍微落後，failover 時也可能遺失最後一小段寫入。
