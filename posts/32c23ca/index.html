JVM Safepoint 完整解析：GC 停頓、Counted Loop 與 Safepoint Timeout 排查

發表於 2023-03-01 更新於 2026-11-26 分類於 JVM 閱讀次數： Disqus： 文章字數： 4k 所需閱讀時間 ≈ 7 分鐘

線上服務偶爾整個卡住好幾秒，GC log 卻顯示 GC 本身只花了幾毫秒？問題很可能不在 GC，而在 Safepoint。這篇整理 Safepoint 的原理、怎麼從 log 判斷是不是 Safepoint 造成的停頓、Counted Loop 為什麼會拖住整個 JVM，以及實際用 SafepointTimeout 抓出卡住的 thread 的過程。

什麼是 Safepoint

JVM 做 GC 時要先找出所有 GC Roots，也就是 thread stack 和暫存器裡指向 heap 的 reference。HotSpot 用一組叫 OopMap 的資料結構記錄「在這個指令位置，哪些 stack slot / 暫存器放的是 reference」，這樣就不用整個 stack 一格一格去猜，可以快速且準確地完成 GC Roots 掃描。

但程式執行過程中 reference 隨時在變，HotSpot 不可能在每一行指令都產生 OopMap，只會在一些特定的指令位置記錄，這些位置就叫 Safepoint。在 Safepoint 上，JVM 完全清楚這個 thread 正在使用哪些 reference，可以安全地掃描甚至搬動物件。

HotSpot 主要在這些地方放 Safepoint：

  • 方法返回之前
  • Uncounted loop 每次回跳（back-edge）之前
  • 呼叫其他方法的位置
  • 執行 native 程式碼或被 block 的 thread，本身就視為已在 Safepoint

Safepoint 為什麼會造成 Stop-the-World

需要做全域操作時，JVM 會先設定一個旗標，然後等待所有 Java thread 跑到最近的 Safepoint 停下來。每個 thread 抵達 Safepoint 的時間不一樣，先到的要等後到的，全部到齊後才開始真正的工作。

所以一次停頓其實分成兩段：

階段說明
Time To Safepoint（TTSP）從發出請求到所有 thread 都停下來的時間
VM Operation真正的工作，例如 GC

只要有一個 thread 遲遲到不了 Safepoint，其他已經停下來的 thread 就全部陪著等，整個應用程式看起來就是「卡住」。

需要 Safepoint 的不只 GC，還包括 deoptimization、class redefinition、jstack 產生 thread dump、biased lock revocation（JDK 15 起預設關閉 biased locking）等操作。

從 log 判斷是不是 Safepoint 的問題

PrintGCApplicationStoppedTime（JDK 8）

加上 -XX:+PrintGCApplicationStoppedTime 後，gc.log 會印出每次停頓的總時間：

  • Total time ... stopped：這次 Stop-the-World 的總時間，不只是 GC，所有 Safepoint 操作都算在內。
  • Stopping threads took：就是 TTSP，等所有 thread 停下來花的時間。

判斷方式：如果停頓很長，但 Stopping threads took 佔了大部分，問題就不是 GC 太慢，而是有 thread 很晚才進 Safepoint。

PrintSafepointStatistics（JDK 8）

在 Tomcat 的 catalina.out 可以看到每次 Safepoint 的統計：

重點欄位：

  • vmop：這次 Safepoint 要做的操作，例如 G1IncCollectionPause、RevokeBias、no vm operation
  • initially_running / wait_to_block：發出請求時還在跑、需要等待的 thread 數
  • spin / block / sync：等待 thread 停下來的時間（毫秒），sync 很大就代表 TTSP 很長
  • vmop（time 欄）：真正操作花的時間

Counted Loop：最常見的元兇

JIT（C2）為了效能，會把「看起來很短」的迴圈當成 Counted Loop，並拿掉迴圈內的 Safepoint 檢查。

Counted LoopUncounted Loop
典型寫法int 當 index、上下界固定的 forlong 當 index，或 while 等條件不固定的迴圈
迴圈內的 Safepoint沒有每次回跳前都有
效能較快每圈多一次檢查

問題發生在：某個 thread 正在跑一個很大的 Counted Loop，迴圈內的方法呼叫又都被 inline 掉了，這時 JVM 要做 GC，這個 thread 必須把整個迴圈跑完才能到達下一個 Safepoint，其他所有 thread 只能一起等，造成長時間的 Stop-the-World。

解法

1. -XX:+UseCountedLoopSafepoints

強制 JIT 在 Counted Loop 的回跳前也放 Safepoint，即使迴圈很小也一樣，避免大迴圈卡住進入 Safepoint。JDK 8u131 修正了這個參數相關的 bug，建議至少升到這個版本再使用。

實測心得：在我們的環境中，這個參數只能延緩問題發生的時間（約一天），並減少發生次數，無法完全根治。最後還是要搭配設定足夠的 Heap memory，降低 GC 的頻率和壓力，才避免了卡住的狀況。

2. 升級到 JDK 10 以上（Loop Strip Mining）

JDK 10 在 C2 加入了 Loop Strip Mining：把大的 Counted Loop 切成每 N 圈（-XX:LoopStripMiningIter，預設 1000）一段，每段結束時檢查一次 Safepoint，兼顧效能與 TTSP。使用 G1、ZGC、Shenandoah 時預設就會開啟。這是比較根本的解法。

3. 調整程式

  • 很長的迴圈改用 long 當 index，讓它成為 Uncounted Loop
  • 把大迴圈拆成多段，或在迴圈中呼叫不會被 inline 的方法

排查流程總結

  1. 開啟停頓 log：JDK 8 用 PrintGCApplicationStoppedTime，JDK 9+ 用 -Xlog:safepoint
  2. 比較總停頓時間和 Stopping threads took：TTSP 佔大部分就是 Safepoint 問題，不是 GC 問題
  3. 用 PrintSafepointStatistics 確認是哪種 vmop、sync 時間多長
  4. 用 SafepointTimeout 找出遲遲不進 Safepoint 的 thread
  5. 修正：調整迴圈寫法、UseCountedLoopSafepoints，最根本的是升級到 JDK 10+，並確保 Heap 足夠
