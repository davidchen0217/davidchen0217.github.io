Clean Code 編排：垂直與水平排版、縮排與團隊準則（完整筆記）

發表於 2024-11-02 更新於 2026-11-26 分類於 CleanCode 閱讀次數： Disqus： 文章字數： 3.2k 所需閱讀時間 ≈ 6 分鐘

這篇是《Clean Code》第 5 章「編排」的完整閱讀筆記：檔案該多長、為什麼原始檔要寫得像報紙、空白行和垂直距離怎麼安排、函式的上下順序、一行該多寬、要不要對齊、縮排與團隊共同準則，最後附上一份編排檢查清單。

編排的目的

程式的編排很重要，它是一種溝通，而溝通是專業開發者的首要之務。

今天寫的功能，很可能在下一個版本就被修改，但程式碼的可讀性會對之後每一次修改產生深遠的影響。程式碼的風格和可讀性會立下先例，持續影響可維護性和可擴充性。就算程式碼已經改到認不出原本的樣子，甚至已經消失，你的風格和紀律依然會留下來。

垂直的編排

檔案該多長？

在 Java 裡，檔案大小和類別大小差不多。比較幾個知名專案：

  • JUnit：由相對小的檔案組成，沒有超過 500 行的檔案，大多數少於 200 行
  • Tomcat、Ant：有些檔案長達數千行，將近一半的檔案超過 200 行

這告訴我們：用大多數 200 行、最長不超過 500 行的檔案，也能建構重要的大型系統。這不是硬性規定，但值得遵守，因為短的檔案通常比長的檔案容易理解。

報紙的啟發

我們希望原始檔讀起來像一篇報紙文章：

  • 名稱簡單易懂、有足夠說明性，光看名稱就知道自己是不是在正確的模組裡
  • 最上方提供高階的概念和演算法
  • 越往下，細節慢慢呈現，直到最底層的函式和細節

一份報紙由很多篇文章組成，大部分都很短，有些稍長，只有極少數會佔滿整個版面。正是這樣的編排讓報紙好用。

用空白行區隔概念

程式幾乎都是由上往下、由左往右閱讀。每一行是一個表達式或子句，每一段程式碼代表一個完整的思緒，思緒之間應該用空白行分隔。

空白行是視覺上的提示：告訴讀者後面接著一個新的、不同的概念，眼光也會自然被吸引到空白行後的第一行。

垂直密度

空白行用來分隔概念，垂直密度則代表關聯的緊密程度：關係密切的程式碼應該緊靠在一起。

垂直距離

關係密切的概念，彼此的垂直距離應該很近，免得讀者在檔案裡上下跳來跳去。

變數宣告：應該盡量靠近使用它的地方。因為函式通常很短，區域變數就宣告在函式最上方：

實體變數：設計良好的類別裡，大部分方法都會用到實體變數。最重要的是把它們宣告在大家都熟悉的位置（Java 慣例是類別最上方），讓人知道去哪裡找。

相依的函式：如果一個函式呼叫另一個函式，兩者應該垂直靠近，而且呼叫者在被呼叫者上方。這樣程式就有自然的順序，被呼叫的函式很好找，整個模組也更好讀。

概念相似性：有些程式碼因為概念相似，希望彼此靠近。相似性越高，垂直距離越短。除了「函式呼叫函式」或「函式使用變數」之外，一組執行類似工作的函式也有相似性。例如同一個類別裡有好幾個方法，命名規則相同、做的是同一件基本工作的不同變化，即使它們沒有互相呼叫，也應該放在一起。

垂直的順序

函式呼叫應該呈現向下的相依性：被呼叫的函式放在呼叫它的函式下方。這樣由上往下讀，會先看到高層的模組，再看到低層的模組。

就像報紙文章，最重要的概念先出現，用最少的細節表達；最底層的細節最後出現。這讓我們可以快速略讀整個檔案，從最前面幾個函式就抓到重點，不必一開始就陷入細節。

水平的編排

一行該多寬？

原則是不需要往右捲動。現在螢幕很寬，字型也可以縮很小，一行甚至能塞到 200 個字元，但別這麼做。上限建議 120 個字元。

水平的空白與密度

用空白表示「分開」，不加空白表示「緊密相關」：

  • 設定運算子兩側加空白：讓左邊和右邊這兩個重要元素的分隔更明顯
  • 函式名稱和左括號之間不加空白：函式和參數高度相關，加了空白反而像是分開的
  • 參數之間在逗號後加空白：強調參數彼此是分開的

水平的對齊

這種對齊一點幫助都沒有，它強調了不該注意的東西：目光會不自覺地由上往下讀一整排變數名稱，反而忽略了型態。更糟的是，自動排版工具通常會把這種對齊弄亂。

如果一串宣告長到「需要對齊才好讀」，真正的問題是宣告太多，代表這個類別該拆了，而不是對齊不夠漂亮。

縮排

原始檔是有階層的：檔案、類別、方法、區塊。工程師非常依賴縮排，從左邊界掃描，靠縮排層次看出每一行屬於哪個範圍，快速找到新的方法宣告、新的變數、新的類別。沒有縮排，程式幾乎無法閱讀。

空的範圍

while 或 for 的本體有時是空的，這種結構最好避免。真的無法避免時，要讓空的本體也有適當的縮排並用大括號包起來，不要把分號藏在同一行尾巴，很容易看漏：

團隊的共同準則

每個人都有自己偏好的風格，但在團隊裡，團隊的準則優先。

團隊應該一起決定一種編排風格，所有成員都照著用。我們不希望軟體看起來像是一群意見不合的人各自寫出來的。

好的軟體系統就像一套可讀性良好的文件，需要一致、順暢的風格。讀者要能相信：在某個檔案看到的編排代表什麼意思，在其他檔案也代表同樣的意思。不要把個人風格摻進原始碼，那只會讓閱讀變得更複雜。

實務上，最有效的做法是把規則寫進工具：用共用的 IDE formatter 設定、.editorconfig，或在 CI 跑 Checkstyle / Spotless 之類的檢查，讓格式不再需要靠人記。

編排檢查清單

  • 檔案大多在 200 行以內，最長不超過 500 行？
  • 檔案由上往下讀像報紙：高階概念在上，細節在下？
  • 不同概念之間用空白行分隔？
  • 密切相關的程式碼緊靠在一起，沒有被多餘的註解或空行隔開？
  • 區域變數宣告在靠近使用的地方，實體變數集中在類別最上方？
  • 呼叫者在被呼叫者上方，概念相似的函式放在一起？
  • 每行不超過 120 字元，不用往右捲動？
  • 運算子兩側有空白、函式名稱和括號之間沒有空白？
  • 沒有為了對齊而加的空白？
  • 縮排正確，空的迴圈本體也有縮排？
  • 符合團隊共同的格式設定，最好由工具自動檢查？
