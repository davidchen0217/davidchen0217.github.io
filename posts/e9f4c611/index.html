OkHttp 是什麼

OkHttp 是 Square 開發的 HTTP client，預設就很有效率：

  • HTTP/2：對同一個 host 的所有請求共用一條 socket
  • 連線池：沒有 HTTP/2 時，透過重用連線降低延遲
  • 透明的 GZIP：自動壓縮，減少下載量
  • 回應快取：重複的請求可以完全不經過網路

API 採用 fluent builder 和不可變物件設計，同時支援同步阻塞呼叫和非同步 callback 呼叫。

需求：Java 8 以上（Android 5.0 / API 21 以上），依賴 Okio 和 Kotlin 標準函式庫。官方強烈建議持續更新版本，因為 TLS 生態一直在變，HTTP client 保持最新是重要的安全防線。

四種 Timeout 的差別

設定涵蓋範圍預設值
connectTimeout建立 TCP / TLS 連線10 秒
readTimeout兩次讀取資料之間的間隔10 秒
writeTimeout兩次寫入資料之間的間隔10 秒
callTimeout整個呼叫：DNS 查詢、連線、送出 request body、伺服器處理、讀完 response body，包含所有重新導向和重試0（不限制）

readTimeout 和 writeTimeout 算的是「兩次讀寫之間」的間隔，只要對方持續一點一點地送資料，就永遠不會觸發。callTimeout 才是整個請求的總時間上限，而它預設是關閉的。

實際案例：unexpected end of stream 與 callTimeout

我們只設定了 connectTimeout、readTimeout、writeTimeout，某次對方回應：

推測是被對方的 CDN 誤判成有問題的來源，連線被故意掛著不斷線，而且這種狀況不會觸發 connect / read / write 這三種 timeout。結果 HTTP 請求一直不結束，持續佔用執行緒。

解法是設定 callTimeout，替整個請求設一個總時間上限，避免單一請求無限期佔住執行緒。實務上建議一定要設定 callTimeout。

java.lang.IllegalStateException: closed

情境：同一個 response 呼叫了兩次以上 response.body().string()。

升級 4.12.0 後 Tomcat thread pool 衝到上限

情境：OkHttp 從 4.10.0 升級到 4.12.0 後，高流量的機器大約 4～5 小時後，Tomcat thread pool 會衝到設定上限，造成系統異常；只有一半流量的機器則完全沒事。

分析：追了 OkHttp 底層的程式碼，發現 PING 這個動作是開 Virtual Thread 執行，而我們的 Tomcat 當時設定成使用 Virtual Threads 的 executor（tomcatThreadPoolVirtual）。

檢查清單

  • 整個應用程式共用同一個 OkHttpClient？
  • 每個 Response 都有關閉（try-with-resources）？
  • response.body().string() 只呼叫一次？
  • 有設定 callTimeout，不只 connect / read / write timeout？
  • 自訂 connectionSpecs 時，需要 HTTP 的話有加 CLEARTEXT？
  • 沒有使用 RC4 之類不安全的 cipher，TLS 版本盡量 1.2 以上？
  • 略過憑證驗證的程式碼只存在測試環境？
  • 升級 OkHttp 版本後，在高流量環境觀察 thread pool 和連線數？
