Docker 執行 Tomcat 常見問題：啟動要 7 分鐘、iptables No chain、curl 56 Connection reset、無法刪除 image

發表於 2022-05-19 更新於 2026-11-27 分類於 Docker 閱讀次數： Disqus： 文章字數： 2.3k 所需閱讀時間 ≈ 4 分鐘

這篇整理用 Docker 執行 Tomcat 時遇過的問題：Tomcat container 啟動要花 7 分鐘、啟動時出現 iptables: No chain/target/match by that name、從主機連 container 出現 curl: (56) Recv failure: Connection reset by peer，以及刪除 image 時出現 image is being used by stopped container。

Tomcat container 啟動要 7 分鐘

情境

用 CentOS + JDK + Tomcat 建立的 Docker image，Tomcat 啟動要花約 7 分鐘。只有部署 .war 檔時才會發生，如果是把 .zip 先解壓縮好再放進去就沒有這個問題。

原因與解法：unpackWARs

Tomcat 的 conf/server.xml 裡，<Host> 有一個 unpackWARs 參數：

值行為
true（預設）先把 WAR 解壓縮成目錄，再從目錄執行
false直接從 WAR 檔執行，不解壓縮，執行時讀取資源的效能較差

我們的 image 裡這個參數被設成 false，改回 true 之後，啟動時間從 7 分鐘縮短到 5 秒：

另一個常見原因：亂數熵不足

在 container 或虛擬機裡，Tomcat 啟動慢還有一個很常見的原因：產生 session ID 等需要安全亂數，而 container 裡的熵（entropy）不足，SecureRandom 會卡住等待。log 裡會看到類似：

curl: (56) Recv failure: Connection reset by peer

情境

Docker 使用橋接（bridge）網路模式，從主機用 curl 連 container 對外開放的 port 時出現：

原因

TCP 連線有建立，但 container 裡沒有程式在對應的 port 上回應，連線被重置。我們遇到的是兩邊的 port 設定不一致：

  • docker-compose.yml 的 port 對應（主機:container）
  • Tomcat server.xml 裡 Connector 實際監聽的 port

例如 compose 寫 8080:8080，但 Tomcat 實際監聽的是 8081。

檢查方式

  1. 對照 docker-compose.yml 的 ports 和 server.xml 的 <Connector port="...">，container 端的 port 要一致
  2. 進到 container 裡確認程式真的在監聽那個 port
  3. 程式要監聽 0.0.0.0，不是 127.0.0.1；只監聽 localhost 的話，從 container 外面連進來也會被重置
